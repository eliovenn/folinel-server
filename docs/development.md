# Folinel 后端开发规范

## 现在从哪里开始

数据库基础、SMTP、邮箱注册验证和会话已完成。下一步继续按小闭环推进：

1. 配置真实运行环境并执行迁移，按 [注册步骤](05-registration.md) 和 [OpenAPI](api/README.md) 接入客户端。
2. 确定管理员初始化与认证方式，再完成受保护的域名规则管理。
3. 做第一项核心业务的创建和读取，只支持当前登录用户自己的数据。
4. 按实际需求补管理后台能力；设备绑定、复杂权限和审计功能在确有需求时加入。

账户主要流程现已明确：邮箱密码登录，注册后邮件验证码验证并自动建立会话。实施前阅读 [账户与邮件设计](03-auth-design.md)，域名限制和 SMTP 方案已确认，邮件模块说明见 [SMTP 步骤](04-smtp.md)。

## 每个功能怎么做

每个功能开始前，先按照根目录 `AGENTS.md` 的“第三方库优先”要求核对现有库及官方插件，记录能力与缺口。有适用实现时优先复用，业务差异通过配置、hook 或 adapter 接入。

每个功能都单独形成一个小闭环：

1. **定义行为**：写清楚角色、前置条件、请求字段、成功响应、错误码、幂等性和权限。
2. **定义数据**：只创建该功能需要的表、索引、约束和时间字段；新业务的日期时间优先使用 `timestamptz`，接口输出 UTC 的 ISO 8601 字符串；时长和点数等数值必须标注单位。鉴权库自有表遵循所选库的 schema。
3. **先写测试**：根据接口实际语义覆盖成功与失败：输入错误、未认证、越权、重复操作或数据库约束等；无需每个接口机械套用全部场景。
4. **实现分层**：路由负责 HTTP 输入输出，service 负责业务规则，repository 负责数据库读写；简单功能可以合并文件，不为了层次创建空文件。
5. **补接口文档**：首个业务接口开始在 `docs/api/` 维护 OpenAPI 契约，明确请求、响应、鉴权、错误和示例。尽量从路由实际使用的校验 schema 生成契约，减少手工维护两套字段；Swagger UI 或 Scalar 只负责展示，接入时再选择。
6. **完成验证**：运行相关测试，再运行 `pnpm typecheck`、`pnpm lint` 和 `pnpm test`。
7. **补步骤文档**：在本文件或功能文档中记录新增配置、迁移、测试命令和已知限制。

一个功能完成后再开始下一个功能。数据库迁移和接口文档属于功能的一部分，不能留到最后集中补。

## API 约定

以下约定已用于注册和当前用户接口；OpenAPI 维护在 `docs/api/`。

- 公开健康检查：`GET /health`。
- 客户端业务接口：`/api/v1/...`。
- 管理后台接口：`/api/admin/v1/...`。
- 成功响应统一使用 `{ "data": ... }`；列表返回明确的 `items`、`total` 或分页结构。
- 项目错误格式为 `{ "error": { "code": "VALIDATION_ERROR", "message": "请求参数无效" } }`，搭配正确 HTTP 状态。基础错误及 404 已统一。响应不返回堆栈、SQL 或凭据。`/api/auth` 原生接口遵循库契约，前置检查错误仍为项目格式。
- 输入在路由边界使用 Zod 校验，服务层接收已解析的类型。
- 时间、金额、点数、分页和排序规则写进接口文档，不依赖前端猜测。
- 不把数据库表结构直接当作公共接口；接口 DTO 单独定义，避免后续数据库重构影响 Flutter。

## 数据库约定

- 本地开发使用 Supabase PostgreSQL，服务器部署时使用服务器 PostgreSQL；两者只通过环境变量切换。
- 密钥只放 `apps/api/config/.env.*` 或部署平台密钥管理中；不提交真实环境文件。
- `pnpm db:check` 只执行只读连接检查。
- 真实数据库测试使用独立的 `TEST_DATABASE_URL`，不能回退到 `DATABASE_URL`。
- 已配置 Drizzle Kit、schema 入口及 `db:generate` / `db:migrate` 脚本。用命令生成及执行迁移，不手动修改 Drizzle 元数据。
- 迁移提交到版本管理，由迁移器记录哪些迁移已经执行；不要求任意 DDL 反复执行。先在独立测试库验证新建和升级路径，文档说明已有数据的处理。运行中的服务不自动迁移。
- 查询默认只取需要的字段；为外部输入的筛选、排序和分页设置边界。
- 不在日志中记录密码、token、Cookie、文章正文、笔记正文或 AI 输入。

## 测试约定

测试使用 Node 内置 `node:test` 和 Supertest。配置测试可以使用假连接串；只有显式设置 `TEST_DATABASE_URL` 才执行真实 PostgreSQL 测试。

测试命名描述行为，不描述实现细节。修复 bug 时先添加能复现问题的测试，再修改代码。可逆的小改动不为了覆盖率添加镜像实现的测试；测试要验证真实边界或用户行为。

## 代码和文档约定

- TypeScript 使用严格模式，Node 原生运行 `.ts`，导入保留 `.ts` 后缀。
- 注释解释原因、单位、调用顺序和安全边界，不重复代码表面含义。
- 业务模块按领域放在 `apps/api/src/modules/<领域>/`，不要把所有接口继续堆在一个 router 文件中。
- 中文文档和关键注释保持简洁，避免记录已经废弃的架构。
- 新增环境变量时同时更新 `apps/api/config/.env.example`、相关本地配置说明和文档。

## Skill 的使用边界

项目规则以根目录 `AGENTS.md` 和本文件为准。Skill 是可选的专项操作参考，不替代接口契约、可运行测试和实际环境验证。

- 数据库设计阶段可按需使用 Supabase 官方 `supabase-postgres-best-practices`，只采用本项目需要的 PostgreSQL 表、索引、事务和查询规则；不因此引入 Supabase 专用 Auth、Storage 或 RLS 架构。
- 开始管理后台开发时可使用 Vercel 官方 `vercel-react-best-practices`，选用 React/Vite 适用的内容，不迁移为 Next.js。
- 已安装上述两个 skill 到用户级 Codex skills 目录，按对应任务使用。不需要同时添加多个重复的后端、架构或测试 skill。
